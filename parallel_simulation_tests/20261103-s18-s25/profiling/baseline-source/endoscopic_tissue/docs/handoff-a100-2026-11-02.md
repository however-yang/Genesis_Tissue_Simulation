## 1. 项目目标与必须保留的效果

项目位于 `endoscopic_tissue/`，是 Genesis 仓库内独立的内窥镜软组织原型。CUDA 原生核心负责材料、器械接触、夹取、剪切和表面重建；Python 负责场景、训练接口、质量监测与记录；Genesis 主要提供显示和相机。材料求解包含四面体有限元能量、稳定 Neo-Hookean 弹性、应变阻尼和体积保护；不要仅凭文件名 `xpbd_solver.cu` 把它理解成普通弹簧或纯 XPBD。

目标是超过 10 万节点接近 33 Hz，完整一步预算约 30.3 ms。用户最重视真实的局部受压、夹持提拉、摩擦滑脱、回弹和剪切效果，不接受“能变形但像果冻”。

- 材料、摩擦、起切力、网格、子步、迭代预算和验收阈值不能为了提速而降低。
- 起切以两片刃实际共同作用、剪切推进位置与变形组织的接触为依据。保留双刃载荷与随后 2 mm 挤压规则。切口可以歪曲、不规则；不把切口投影或拉成直线。
- `WallCutMeasure` 在静止材料坐标下的偏离量只用于重复性评价，不是约束切口形状的目标。
- 纯摩擦夹取允许真实滑脱；明显具备足够咬合的组织应夹得起来。辅助锚点模式的成功不能代替纯摩擦成功，不能用新增粘连掩盖接触缺陷。
- 一次只改一个原因。保留失败记录，做同机基线/候选无录像计时和完整交互录像；未通过不得覆盖默认库。
- 大改前提交回滚点。其他 GPU 任务在运行时自动等待，不操作别人的进程。暂不接真实机械臂。

## 3. Linux 环境与 A100 编译

### 先准备无界面物理测试

使用 Python 3.10–3.13，优先与旧环境相近的 3.11。旧机器为 RTX 3090、i9-14900K、CUDA Toolkit 12.5、Python 3.11；详细 Python 包版本见 [本机参考环境](../../endoscopic_tissue_backups/2026-11-02-a100-handoff/windows-environment-reference.json)。该文件不是经过验证的 Linux 锁文件。

```bash

sudo apt-get update
sudo apt-get install -y build-essential cmake ninja-build python3-venv libgl1 libglib2.0-0 ffmpeg

source .venv/bin/activate
python -m pip install --upgrade pip
H=endoscopic_tissue_backups/2026-11-02-a100-handoff

python -m pip install -r "$H/requirements-core.txt"

python -m pip freeze > endoscopic_tissue/outputs/a100-migration/linux-pip-freeze.txt

```

`nvidia-smi` 的 CUDA 字段不能证明本机安装了 `nvcc`。缺少 Toolkit 时按 [NVIDIA CUDA 12.5 Linux 安装说明](https://docs.nvidia.com/cuda/archive/12.5.1/cuda-installation-guide-linux/index.html)选择与实际 Ubuntu/GCC/驱动兼容的配置。此处以接近原 12.5 环境减少变量，不要求盲目降级已有可用环境。

A100 的计算能力为 **8.0**，RTX 3090 为 8.6；原 CMake 写死 `86`，不能原样搬过去。迁移工具默认 `80`，依据 [NVIDIA 架构表](https://developer.nvidia.com/cuda/gpus) 和 [CMake CUDA_ARCHITECTURES](https://cmake.org/cmake/help/latest/prop_tgt/CUDA_ARCHITECTURES.html)。

### 构建基线及快照实验基线

以下命令全部在仓库根目录执行。先构建这两版；确认它们在新机器可运行后，再构建候选。`prepare_source.py` 拒绝覆盖已有生成目录，重复试验请保存旧目录并明确使用新实验目录或新检查点。

```bash
set -euo pipefail
for V in contact-groups31 training-snapshot1; do
  python "$H/prepare_source.py" --variant "$V"
  W="$PWD/endoscopic_tissue/outputs/a100-migration/$V"
  cmake -S "$W/source" -B "$W/build" -G Ninja \
    -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_COMPILER="$(command -v nvcc)"
  cmake --build "$W/build" --parallel 4
  file "$W/build/lib/libLiverCudaSim.so"
  ldd "$W/build/lib/libLiverCudaSim.so"
  sha256sum "$W/build/lib/libLiverCudaSim.so" > "$W/library.sha256"
done
```

若有任何构建错误，停止后续运行并保存日志，不能把“源码准备成功”写成“编译成功”。可先单独运行 `python "$H/prepare_source.py" --variant training-snapshot1 --verify-only` 核对包。

迁移只改生成副本中的 C 导出声明和 CMake：去除非 MSVC 编译器的 `/utf-8` 参数、使用 `sm_80`、输出 `.so`。候选在 `cut.cu`、`dc_recon.cu` 中还有直接导出的 C 函数，也只改其导出声明。所有计算核函数、材料、接触和剪切规则均按冻结源码保留。移植后仍需实测数值与性能，不能由源码相同推断跨平台结果相同。

构建目录还会生成 `LiverCudaSim.dll -> libLiverCudaSim.so` 的 Linux 符号链接，供旧验收脚本固定的文件名使用。它实际指向 ELF `.so`，不是 Windows DLL。传给旧脚本 `--dll` 的是该目录的**绝对路径**。不要复制进默认 `native/bin*`。

原来的 `build_native.py`、`build_candidate.py`、`.cmd` 构建器是 Windows 专用；不要在 Linux 原样执行。旧准备脚本有文本换行依赖，Linux 首轮直接用此次冻结包，不必重新生成旧状态清单。

```bash

BASE="$PWD/endoscopic_tissue/outputs/a100-migration/contact-groups31/build/lib"
SNAP="$PWD/endoscopic_tissue/outputs/a100-migration/training-snapshot1/build/lib"

# 先跑完整物理与质量检查，无录像；hold 是此场景的最后阶段。
python "$P/damage_trial.py" --name a100-base-three-r0 --dll "$BASE" \
  --scene wall-traction --stop-after hold
python "$P/damage_trial.py" --name a100-snapshot-three-r0 --dll "$SNAP" \

python "$P/damage_trial.py" --name a100-snapshot-three-video-r0 --dll "$SNAP" \

```

每个 `--name` 只用一次，输出在 `endoscopic_tissue/outputs/acceptance-fixes-20261102/<name>/`；沿用旧日期只是脚本固定的输出位置。失败返回非零、`passed=false`，需保留整个目录。完整墙面牵拉通常为 1440 个原生步、排除准备的 1410 条转移、录像含初始帧共 1441 帧。查看 `result.json`、`steps.json`、`preparation.json` 和 `context.json`，不能仅看进程退出或视频能播放。

上述裸 worker 命令不会自动等待 GPU；执行前确认 GPU 空闲，并在运行中记录其他进程和利用率。旧 Windows 队列/CPU 亲和性脚本不能直接当作 Linux 监控器。并发污染的运行保留为诊断，不用于帧率验收。一次只运行一个原生会话；不要在一个 Python 进程中同时加载多个此类库。

### 快照、组织瓣与换抓

```bash
python "$H/check_snapshot.py" --name a100-snapshot-wall-r0 --library-dir "$SNAP"
python "$H/check_snapshot.py" --name a100-snapshot-flap-r0 --library-dir "$SNAP" --scene flap
python "$P/regrasp_trial.py" --name a100-regrasp-r0 --dll "$SNAP" --repeat 0 --capture
```

`check_snapshot.py` 调用原有 T1/T2/T3/T5/T6/新会话和资源测试，避开旧包装器的 `kernel32` CPU 拓扑探测，不改验收线。冒烟、完整轨迹通过之后再运行：

```bash
python "$H/check_snapshot.py" --name a100-snapshot-resources-r0 \
  --library-dir "$SNAP" --resources 1000
```

T8 要用单 GPU 环境，旧资源读取器取 `nvidia-smi` 返回的第一张卡；多卡机器必须先使内存统计与实际测试 GPU 一致，不能拿另一张卡的数值验收。资源与录像输出可能很大，先确认剩余空间。

快照严格绑定库 SHA、ABI、物理配置及 Python 状态。**禁止**把 Windows 的 `.lcssnap` 直接恢复到 Linux 或另一个候选。每次在 A100 对应库上重新准备并保存；旧现场只用于离线分析。不能改哈希或关闭校验来绕过绑定。

### 两个未通过候选如何继续

需要复现时，将第 3 节构建循环中的版本分别换成 `boundary-snapshot2`、`repair-feasible-snapshot3`，得到各自的独立 `build/lib`，再用绝对路径替换上面命令的 `$SNAP`，并换新输出名字。先完整三剪、重复换抓、wall/flap 快照，再决定是否做耗时 ABBA。不要仅跑十几步就进入大规模性能优化。

## 5. 完整交互录像与显示

无界面物理检查不要求 Genesis 渲染环境。录像的 `--capture` 保存几何/器械状态，本身不代表已经生成 MP4。需要生成图像时，另外安装本仓库 Genesis 依赖：

```bash
# 先按驱动条件安装 PyTorch；以下与旧环境的 torch 2.8 / cu126 相近。
python -m pip install torch==2.8.0 --index-url https://download.pytorch.org/whl/cu126
python -m pip install -e .
python -m pip install scipy imageio-ffmpeg
```

PyTorch 的 CUDA wheel 与编译原生库使用的 CUDA Toolkit 是两回事；以上 cu126 需要机器驱动支持，安装选择见 [PyTorch 官方历史版本说明](https://pytorch.org/get-started/previous-versions/)。不要为了渲染安装去覆盖已有驱动。

Linux/A100 服务器的 EGL/OpenGL 能否创建相机尚未验证。先确认服务器图形环境；有可用 EGL 时可尝试：

```bash
export PYOPENGL_PLATFORM=egl
O="$PWD/endoscopic_tissue/outputs/acceptance-fixes-20261102"
python "$P/render_capture.py" "$O/a100-snapshot-three-video-r0"

```

输出为 `review/interactions-h264.mp4` 和 `review/video-verification.json`。渲染器核对逐步记录、全部帧数、完整解码与文件 SHA。若 A100 无法建立图形上下文，可以把完整捕获目录传回具备已验证渲染环境的 Windows 机器离线渲染；这不需要重新执行物理。跨平台回放仍应先核对 Python/数组版本与捕获哈希，保留原文件。软件渲染或离线编码耗时不算原生物理 FPS。

两版都生成完整视频后，用现有工具并排对照，例如：

```bash
python "$P/compare_videos.py" --name a100-three-comparison-r0 \
  --baseline a100-baseline-video-r0 --candidate a100-candidate-video-r0
```

这两个名字必须对应之前实际录制并成功渲染的目录；示例不会替你创建它们。工具拒绝通过截短或变速使不同长度的录像相符。视频 30 fps 是仿真时间播放速率，不能当作系统达到 30/33 Hz 的证据。

需检查全程接近、咬合、闭合、提拉、各次起切、换位、退刀、真正松开夹爪、组织回落和重新夹取。墙面三剪中的 `release` 主要是剪刀开合，夹爪仍闭合，不能据此关闭“切除后松夹穿入”问题。已复核的分镜没有明显整体果冻摆动，不等于逐帧或与真实手术视频已建立定量等价。

### 失败现场已经学到什么

`regrasp-boundary-r1` 的刀体重叠最大值约 0.325729 / 0.267715 mm（原/恢复），既定线 0.2 mm；未出现非法四面体或局部范围失败也不能记为通过。另一轮失败现场 tick 954 的重叠约 0.203380 mm，邻近四面体接近现有 `minJ=0.15` 保护下限。

最终表面三角形会因 GPU 原子操作重新排序。分析接触应按材料体素、连通分量和真实切边身份匹配，不能拿三角形下标直接对齐。应读 `native-contact-final.json`；更早的同目录 `native-contact.json` 含错误下标匹配，不能引用其大误差。

有效接触在失败位置已经存在，嵌入误差约 0.004–0.010 mm。因此不能简单认定“接触完全漏检”。`repair-feasible-snapshot3` 只在重建接触的两条粗方向前添加已有可行分组/权重处理，不改变目标、摩擦、体积下限或迭代数。但离线现场中 35 个接近体积下限的四面体对应已保存权重均为 1，模拟分组后没有改变权重。这个负面结果削弱了原假设；不能把候选包装成已找到根因，更不能默认它一定提速。

### S15 未完成的硬验收

- T3：最大节点续跑差 < 0.01 mm；不能只选材料子集或改阈值隐藏全节点失败。
- T4：接触前、首次起切后、挤压中、换抓后各 20 对；中位数差 ΔL ≤ 0.8 mm、起切 ≤ 5 步、偏离 ≤ 0.16 mm，另报 KS。
- T7：同一个不可变 cut-ready 缓存与 20 次重新准备比较。
- T8：1000 次存取，200 次预热后看 RSS 斜率 ≤ 1 KiB/次、净增 ≤ 8 MiB，GPU 增长 ≤ 64 MiB，原生分配清单完全一致；最大恢复耗时 < 11.5 s。目标恢复 ≤ 1 s、压缩快照 ≤ 200 MB。
- 小样本、跳过、提前停止、外部任务干扰不能算完整通过；不要在队列看到进度就自动推广默认版本。

最近一组干净的 Windows/3090 墙面 ABBA：76,050 个总网格节点，其中 30,417 个材料节点，完整质量检查，无录像；每版仅两次独立运行。见 [完整计时摘要](../../endoscopic_tissue_backups/2026-11-02-a100-handoff/evidence/boundary-controlled-summary.json)。

这只能说明该组总耗时均值约下降 3.56%，不证明整体验收或稳定不退化。原生最大值的两轮均值反而上升约 3.64%，候选也有交互质量失败。更早一组基线两轮约 87.3 / 52.2 ms，存在明显漂移，保留但不作速度签署。

后续先分解同一步重复的表面导出、邻接/连通性统计、数组复制和器械几何计算，验证复用前后输出一致。只缓存真正不变的数据；依赖当前坐标的拓扑统计不能仅按拓扑版本跨帧缓存。然后再逐核分析材料求解、接触搜索/修复、切割、重建、同步与读回。大改算法保持独立构建和前置 commit。

对候选计时采用同一 A100、同一驱动/编译器/参数/动作/检查模式，基线 A1 → 候选 B1 → 候选 B2 → 基线 A2，重复完整组；录像另跑。报告各阶段均值、中位数、P95、P99、最大值和真实进程/GPU 占用。不能拿 3090 与 A100 的差值当算法收益，不能把数千相关帧当数千独立试验。

历史肾脏大场景约 121,260 活动节点、102,710 材料节点、1 mm 网格，尚有松夹/释放质量缺口。待墙面回归稳定后，使用显式指定的库进入 `python -m endoscopic_tissue.run --scene kidney --demo --dll <绝对.so路径>`；该入口导入渲染依赖，即使 `--native-only` 也须先解决导入环境。分别报告纯物理、含质量检查和含显示整链路的速度；只有最后一种才可与用户观察的实时帧率直接比较。
