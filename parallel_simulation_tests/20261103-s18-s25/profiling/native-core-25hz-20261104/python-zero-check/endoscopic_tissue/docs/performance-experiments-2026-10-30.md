## 集成异常定位与运行作用域修复

原始候选有 2 次访问异常、2 次完整运行；三个冻结基线双线程运行完成。崩溃栈落在异步几何检查，Windows Application Error 事件明确给出故障模块 `libscipy_openblas64_-63c857e738469261263c764a36be9436.dll`，异常码 `c0000005`、偏移 `0x6b4668` / `0x6b467d`。既往同进程录制崩溃日志也指向该模块，不能再将这些事件笼统归为 OpenGL 崩溃。

NumPy 所带 OpenBLAS 为 `0.3.31.188.0`、pthreads、24 线程；SciPy 另带 OpenBLAS `0.3.30`。与本机同版本的并发矩阵运算问题见 [NumPy #31618](https://github.com/numpy/numpy/issues/31618)，单线程 BLAS 是该问题记录中的有效对照；[OpenBLAS 官方 FAQ](https://www.openmathlib.org/OpenBLAS/docs/faq/#how-can-i-use-openblas-in-multi-threaded-applications) 也建议已具有应用线程的程序控制内部 BLAS 并行。日志定位是本机证据，与上游问题对应的具体竞争机制仍属推断。

在 `run.main` 整个运行作用域内采用 `threadpool_limits.wrap(limits=1, user_api="blas")`，在创建工作线程前生效，所有工作线程退出后恢复原线程设置；依赖显式声明 `threadpoolctl>=3.6`。不改系统环境、不替换任何库、不更改 CUDA 物理参数。已验证修复后的基线和六次候选运行中，两个 BLAS 均为 1 线程，退出后恢复为 24；六次候选均完整完成 1110 步，未再出现访问异常。这是本机本轮复测结果，不能保证所有硬件和任意运行时长均无异常。限定线程后的候选回放仍是 1111/1111 帧与首轮基线原始图像哈希一致；另一次单刀与剪刀共 18 项边界显示检查也逐像素一致。最终默认渲染文件与被测候选逐字节一致。
